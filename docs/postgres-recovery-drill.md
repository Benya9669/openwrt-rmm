# Проверка восстановления PostgreSQL

`scripts/verify-postgres-backup.sh` восстанавливает custom-format `pg_dump` в новый
одноразовый PostgreSQL. Скрипт не подключается к рабочей БД, не публикует порты и
создаёт отдельную internal Docker network. После проверки удаляются только созданные
им контейнеры, их одноразовые тома и сеть. Обработчики сигналов выполняют ту же
очистку; после аварийного завершения Docker/хоста ресурсы могут остаться и требуют
ручной проверки перед удалением.

## Что подготовить

- Linux, Bash, Docker и утилиты `sha256sum`, `realpath`, `mktemp`, `od`, `tr`.
- Custom-format дамп, например полученный `scripts/backup-postgres.sh`, и его
  SHA-256 из сохранённого рядом файла. Проверяйте происхождение контрольной суммы.
- **Существующие ключи того же сервера**: `data-encryption.key` и
  `command-signing-ed25519.pem`. Скопируйте их безопасным способом в закрытый
  каталог на машине проверки. Новые ключи не заменяют потерянные старые.
- Доверенный образ сервера с `/usr/local/bin/rmm-db-verify`, собранный из той же
  версии схемы. Образ PostgreSQL должен поддерживать версию исходного дампа;
  для регулярной проверки используйте ту же major-версию (CI проверяет 16 и 18).
- Место для восстановленной БД и память для самой большой зашифрованной копии
  устройства. Секретные входные файлы монтируются только для чтения.

Не загружайте рабочие дампы и ключи в Git или публичный CI. Скрипт предназначен
для доверенных дампов RMM и доверенных образов; восстановление SQL-дампа выполняет
его SQL. TLS отключён только между одноразовыми контейнерами закрытой тестовой
сети, без опубликованных портов.

## Запуск

Из корня репозитория соберите образ проверки. Это не обновляет работающий сервер:

```sh
docker build -t rmm-recovery-check .
umask 077
bash scripts/verify-postgres-backup.sh \
  --dump /secure/recovery/rmm.dump \
  --sha256 '<64 hex characters from the saved SHA-256 file>' \
  --encryption-key /secure/recovery/data-encryption.key \
  --signing-key /secure/recovery/command-signing-ed25519.pem \
  --image rmm-recovery-check \
  --postgres-image postgres:18 \
  --dry-run
```

После проверки путей и суммы повторите команду без `--dry-run`. При успехе stdout
содержит JSON с количеством строк и SHA-256 содержимого каждой таблицы, количеством
проверенных подписанных команд и зашифрованных архивов. Код выхода — `0`. Сохранить
отчёт можно через `> /secure/recovery/report.json` с указанным `umask`; используйте
новое имя файла, чтобы не перезаписать предыдущий отчёт.

Проверяются точный набор/checksum миграций, совпадение обоих key ID, все сохранённые
подписи команд, расшифровка всех архивов и совпадение их plaintext SHA-256/размера.
Для остальных зашифрованных полей выполняется выборочная проверка по одному
значению каждого поддерживаемого типа. Отчёт содержит агрегаты и хеши, без токенов,
паролей, содержимого строк, архивов или ключей. Ошибки подключения не печатают DSN.
Проверка выполняется в read-only repeatable-read транзакции и не запускает сервер,
агентов, tunnel reaper или notification workers.

## Сравнение с исходной копией

Без исходного manifest успешная проверка подтверждает читаемость и внутреннюю
согласованность дампа; она не доказывает, что в дамп попали все ожидаемые записи.
Опциональный `--expected /secure/recovery/expected.json` сравнивает все счётчики и
хеши с отчётом `rmm-db-verify` из **того же неизменяемого состояния БД**. Для
получения исходного отчёта и дампа остановите записи либо используйте отдельную
замороженную копию. Дамп и отчёт, полученные последовательно на изменяющейся
рабочей БД, могут закономерно различаться.

Сам инструмент получает соединение через `RMM_RECOVERY_DATABASE_URL` и аргументы
`--encryption-key FILE --signing-key FILE [--expected FILE]`. Передавайте DSN через
защищённое окружение, не аргументы командной строки или историю shell. Используйте
его на копии: полный проход и хеширование таблиц создают нагрузку.

## CI и ограничения

`.github/workflows/postgres.yml` создаёт синтетическую БД с оператором, устройством,
подписанной командой и зашифрованным архивом. Реальные `pg_dump`/`pg_restore`
выполняются клиентом соответствующей версии 16/18. Сравниваются все таблицы,
проверяются login и heartbeat после восстановления, чужие ключи и повреждённые
подписи/архивы. Затем тот же дамп проходит полный Bash-скрипт в отдельной сети;
неверная SHA-256 отклоняется до создания ресурсов.

Для локального Go integration test задайте `RMM_TEST_POSTGRES_CONTAINER` (ID
созданного тестового Docker-контейнера, пользователь `rmm_test`),
`RMM_TEST_POSTGRES_RECOVERY_SOURCE_URL` и `RMM_TEST_POSTGRES_RECOVERY_TARGET_URL`.
Обе БД должны быть пустыми, на loopback с `sslmode=disable`, и называться
`rmm_recovery_source` / `rmm_recovery_target`. Для проверки Bash-скрипта также
задайте `RMM_TEST_RECOVERY_IMAGE` и `RMM_TEST_RECOVERY_POSTGRES_IMAGE`.

```sh
go test -count=1 -v ./server/internal/dbmigrate -run TestPostgresRecoveryIntegration
```

Тесты оставляют записи в двух указанных БД; для повторения создайте новый
одноразовый контейнер. Проверка настоящего production-бэкапа и измерение времени
восстановления на его объёме остаются отдельным эксплуатационным шагом.
